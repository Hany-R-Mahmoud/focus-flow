## Critical blockers before merge or production switch
1. [ ] Google Cloud Console OAuth Web client and consent screen configured by Codex, with exact `{NEON_AUTH_BASE_URL}/callback/google` URI. Set its client ID/secret **inside Neon Auth** (not Vercel browser env or GitHub), replacing shared development credentials.
2. [ ] Configure a **custom SMTP/email provider** in Neon Auth for reliable password reset and verification messages. Enable required email verification once it has been tested. Neon shared development sender cannot be relied on for production delivery.
3. [ ] Run authenticated browser/device E2E tests (including new account, login, session refresh, Google, forgotten password, verification, reset, logout, guest). Unit tests alone are insufficient for OAuth and external email.
4. [ ] Exercise cloud collaboration with **two distinct signed-in accounts**: create, retrieve, join, conflict names, roster refresh, leave/reconnect, owner delete, non-owner delete denial, third-party read/write denial and rate-limit exhaustion. Exercise guest local invites while signed in and signed out. Verify no personal IndexedDB data disappears on sign in/out.
5. [ ] Regenerate and commit `pnpm-lock.yaml` using the pinned pnpm toolchain after `pnpm install`. Revert temporary Vercel `installCommand` to `pnpm install --frozen-lockfile`, and rebuild. Current `--no-frozen-lockfile` is only a *preview compatibility workaround* because the lockfile wasn't regenerated by the app connector.
6. [ ] Set up a genuinely isolated preview auth backend; the attempted child database branch `br-silent-sunset-b90ziqjl` inherited `neon_auth` schema, and `provision_neon_auth` was refused due to existing schema. Do not test destructive Auth changes there. Vercel Preview `VITE_NEON_URL` has been updated to the separate preview project. Verify a newly-built preview before running account E2E. No destructive database reset authorized.
7. [ ] Review beta SDK dependencies (Neon JS `0.8.0-beta`) and peer version warnings; pin a tested compatible version/lockfile.
8. [ ] Verify secure domains, allowed redirect URLs, production cookies, RLS and function `EXECUTE` privileges. Current group requests require valid Neon Auth identity and server-side per-user database rate limits; they do not include CAPTCHA; consider IP-based protection against account-creation abuse separately.
9. [ ] Update project-wide older product/handover docs and tests that still use Supabase terminology.
10. [ ] After these gates: configure **production** `VITE_NEON_URL` public HTTPS base, remove obsolete Vercel Supabase/Turnstile environment variables, build a staged production deployment and test it, promote the tested version, verify runtime logs and browser flows, retain previous production Vercel release for rollback.

## Data model and rollback
- Anonymous guest: local IndexedDB for personal data, payload-based shareable links, browser-local participant state.
- Signed-in: same private local data + Neon Auth for identity + Neon for cloud group sessions and live membership. No automatic cross-device private-data synchronization is implemented.
- Legacy Supabase source data intentionally not imported on owner instruction. Production has not cut over. Rollback at this stage simply requires continuing to use the existing `main` production Vercel release; do not delete databases until independently verified.
